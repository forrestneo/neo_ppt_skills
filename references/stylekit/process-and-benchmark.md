> 定位：`audit-protocol.md` 管"稿子怎么验收"，本篇管**过程怎么可信**——状态与视觉

> PPT 技能"。

## 一、双信号验证（JSON 不是视觉 QA）

报告任务完成前，两个信号缺一不可：

1. **状态信号**：读权威状态（项目/运行的规范快照），持久任务必须等到终态
   `complete`——`error` 和 `cancelled` 都算未完成；等待超时 ≠ 任务取消。
2. **视觉信号**：打开返回的精确跳转链接（保留 slide/panel/version 等定位参数），
   确认**用户将看到的那一页**真的长成要求的样式。

**只看 JSON 响应不算视觉验收**（"Do not treat a JSON response alone as visual
QA"）。视觉通道不可用时，用持久化产物做结构证据，并**明确声明"可见验证仍未做"**
——与 `audit-protocol.md` 的三态语义（static/rendered/visual）同源。

## 二、故障恢复：先分类，再重试（known-errors 思路）

把踩过的坑写成技能的一个固定章节，失败时**先分类再动手**：

- **禁止假成功**：任何一页状态是 error 或图片加载不出来，不得报整单成功。
- **禁止重建**：浏览器标签关了、等待超时了，都不等于任务丢了——保留项目 id，
  续跑或重新拉起，不要"重新生成一遍"。
- **状态冲突**：两端状态不一致时，以持久化存储为准，然后刷新视图；不要信内存里的旧态。
- **运行互斥**：已有任务在跑就查看/等待/显式取消，不开冲突的新任务。
- **链接不重建**：用返回的精确跳转 URL（含定位参数），不手工拼。
- 版本契约：插件/运行时的版本对不上时先升级再重试（缓存可能过期）。

## 三、结构化采集（intake）的纪律

- **一次采集 = 一个持久项目 + 一份共享澄清状态**，不是一段聊天问卷——答案要落到
  项目状态里，重连后还在。
- **只问实质改变结果的问题**（受众/目的/页数/语言/画幅/研究深度/视觉方向），
  能从场景预设和默认值来的不问；每题带推荐项和可跳过。
- **素材按角色分槽**：内容源、数据集、品牌资产、视觉参考各有各的槽位，
  不许混成一个"上传文件堆"；必填槽位未满足不许开工。
- 采集产物在**昂贵步骤之前**确认：大纲是持久化、可编辑、可确认的 artifact——
  **确认之前不画任何像素**（出图最花钱）。

## 四、过程可见化（checkpoint 可见契约）

- 默认**引导式流程**：澄清 → 大纲确认 → 风格挑选 → 逐页生成，每个 checkpoint
  展示给用户做决定；"实质性改变结果而用户没表态的选择，留着问"。
- **headless 一次性生成是显式 opt-in**，不是默认——不许"给用户看一句'工作中'
  然后后台把整份 deck 做完"。
- 渲染/研究过程中保持工作区可见，用户随时能转向；完成后在同一工作区检查，
  **视觉复查过了才导出**。
- 部分完成的稿子**可续跑**（逐页渲染的天然优势）；中断后从断页继续，不推倒重来。

## 五、版本纪律（改稿历史不可变）

- 每个改变成品的操作（AI 命令、手动修改）都产生一个**不可变版本快照**（含各页
  图、转场、备注）；多步 AI 命令可合并为一个版本，纯对话/翻页/无变化保存不产生空版本。
- **恢复历史 = 以旧版本为源新建当前版本**，绝不覆盖历史。
- 导出永远绑定"当前或显式选定的版本"——导出的就是验收过的那份。
- 演讲备注走原生 PPTX 备注通道（off-canvas，演示者模式可见）。

## 六、PEI 可编辑性分级（评价一个 PPT 技能的第一维度）

来自 SlidesGen-Bench（arXiv 2601.09487）的分级，清单用它给 216 个项目定级：

| 级别 | 含义 |
|---|---|
| L0 | 不可编辑（纯图） |
| L1 | 仅文本可编辑 |
| L2 | 文本 + 简单形状可编辑 |
| L3 | 原生结构化 PPTX（文本/形状/图表均原生） |
| L5+ | Web 幻灯（代码级可编辑，可带动画） |

**核心洞察（清单 31 项实测）**："Content was not where decks differed: 10 of 26
scored 100%. **Pick by whether you can edit the result**."——内容质量不再是差异点
（头部技能都满分），**可编辑性才是**。本技能定位 L3（原生结构化），模式 B/D 出稿
即原生对象；对外宣称能力时按 PEI 口径，不夸大（对照 `edit-fidelity.md` 的能力
显式声明原则）。

## 七、横评方法论（怎么测一个 PPT 技能）

清单 31 项端到端实测的流程，可直接用于本技能的回归验收或竞品对比：

1. **同一 brief**：所有技能跑同一份需求（题目/受众/页数），排除内容变量；
2. **一次性沙箱**：每个技能全新环境、无预设、Claude Code 统一驱动，排除环境差异；
3. **三段排序**：交付前返工量（要人工修几轮才能交付）→ PEI 可编辑性 →
   内容 rubric（PresentBench，arXiv 2603.07244）；
4. **安全分级**：读 README + 安装步骤，标 SAFE / CAUTION / UNSAFE
   （安装脚本行为、外部请求、密钥处理）；
5. 分类法：框架引擎 / 可编辑 PPTX / 图像优先 / Web 幻灯 / 商业咨询 / 文档转
   slides 六类——比较只在同类内进行。

对照本技能：`tests/eval_slim.py` 是结构回归，横评方法补的是"同 brief 横向 +
人工返工量"这个维度——重大改版后值得跑一次。
